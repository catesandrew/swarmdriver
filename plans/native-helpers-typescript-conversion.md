# Plan: True TypeScript conversion for `packages/core/src/helpers/native/*.ts`

Status: **APPROVED (round 4, APPROVE WITH CHANGES) — pending user execution approval**

## Requirements Summary

Eight native helper files (plus a barrel) were ported from JS to TS by extension-swap only. They compile today (`tsc --noEmit` exits 0) because `tsconfig.base.json` has `strict: false` / no `noImplicitAny` — untyped params are silently accepted. Independently verified by both Architect and Codex Critic via `tsc --noImplicitAny`: **78 implicit-any diagnostics inside `helpers/native`** (not the ~30 a manual read finds), plus 125 more elsewhere in `packages/core` (out of scope here, contained by an explicit allowlist — see Step 0).

Goal: make each file *actually* typed (no implicit `any`, no explicit `any` laundering, real parameter/return annotations replacing leftover JSDoc), add vitest coverage that didn't exist before, and verify via a **compiler-enforced ratchet** (not manual audit) after each file.

## Round-1 Review Outcome

Both Architect and Codex Critic independently confirmed the same 78-site count and the same five defects in the original draft:
1. Inventory undercounted implicit-any 2.6x (~30 claimed vs. 78 actual), concentrated in files the original draft called "small/low-risk."
2. `ContextRef` typing was wrong for `web-view.ts` — `switchToContext` is numeric, `findWebviewContext` is string-based; treating them as the same type was incorrect.
3. `findStrategy` returns `{ using, value }`, not `string`.
4. `gestures.ts`'s two explicit `any`s are `reduce()` accumulator annotations (not element-array types), and the code comment explaining them is stale/wrong.
5. File ordering typed every consumer before its producer (`utils.ts`, the shared vocabulary, was scheduled last), guaranteeing rework across already-committed files.

Both reviewers also flagged the same structural gap: `findEle`/`findEles`/`findEleAndSel` (in `utils.ts`) return `false` on failure paths, with 13 unguarded dereference sites across the other files — a direct conflict between Principle 1 ("no behavior changes") and Acceptance Criterion #1 ("zero implicit any") that the original draft deferred to step 8 instead of deciding up front.

All five points plus the structural gap were addressed in the round-2 revision — but the round-2 Architect review found the fixes themselves were flawed in 5 concrete, reproduced ways:

- **B1**: the round-2 `tsconfig.strict.json` (`extends` + `files: []`) does not actually contain scope — `extends` inherits the parent's `include`, so the config resolved 84 files / 203 errors, not the claimed empty set. Fix requires an explicit `"include": []` alongside `"files": []`.
- **B2**: `assertEle()` was specified to apply at all 13 originally-identified `| false` dereference sites, but at least 5 of those sites already guard the result via truthy narrowing (`if (el) {...}`, `if (!el) return false`) — TypeScript automatically narrows the literal `false` out of `WdioElement | false` at a truthy check, so these sites are already type-safe with zero code change. Force-applying `assertEle()` there would have converted a normal "not found yet, keep scrolling" control-flow path (used with zero try/catch anywhere in `gestures.ts`) into an uncaught throw, breaking scroll-to-find on the first miss.
- **B3**: `findEleAndSel` returns `Promise<{el: WdioElement | false; sel: string | false}>` (an object), not `Promise<WdioElement | false>`; `findEles` returns `Promise<WdioElement[] | false>` (an array, since it wraps `$$()`), not the singular element type. `assertEle`'s `selector` parameter must accept `string | undefined` to match `ElementOrSelector.selector`'s existing optionality.
- **B4**: because the honest `| false` union return type takes effect the moment `utils.ts` is retyped, every unguarded consumer across *any* file (not just `utils.ts`) breaks `tsc -p tsconfig.json` (the package-wide, always-green gate) immediately — including files not scheduled for their own conversion step until later. The round-2 plan didn't account for this, so the package-wide gate would fail from that step onward until every consumer file was reached.
- **B5**: the round-2 document stated three different orderings in three places (the numbered step list, a prose re-sequencing note, and a Risks-table row) that directly contradicted each other.

Round 3 fixed B1-B5, and the round-3 review confirmed: B3 fully correct, B4's audit scope provably complete, and all 5 named B2 guarded-site examples verified verbatim against source. But round 3's own fixes had gaps, found by building the actual config rather than reading it:

- **N1 (new)**: `"include": []` — while correctly blocking the inherited `include` — also drops `src/globals.d.ts` from the checked program. That file is the *only* place `driver`/`browser`/`$`/`$$` are declared; without it, 7 of the 8 files (every one that references those ambient globals) fail with `TS2304`/`TS2581` ("cannot find name"), which is unfixable under Decision B1 (forbids touching `globals.d.ts`'s content, but says nothing about needing to include the file that declares it in the checked program).
- **N2 (new, harder)**: TypeScript's `files` array bounds the *root* files fed to the compiler, not the full checked program — anything those root files import is pulled in too. `utils.ts` imports from `../../enums/*` (14 enum files total, of which Step 0 only fixes 2 — `context-ref.ts` and `document-ready-state.ts`, the two `web-view.ts` needs). The other 12 enum files' `TS7053` diagnostics (~70 of them) enter the checked program the moment `utils.ts` is added to `files`, so `tsc -p tsconfig.strict.json` cannot exit 0 from step 2 onward no matter how correctly `utils.ts` itself is typed — measured directly: `files:[utils.ts]` (with N1's `globals.d.ts` fix applied) still produces on the order of 70 diagnostics attributable to those other 12 enum files.
- **B5 residue**: 4 stray references to the old (round-1/round-2) step numbering survived the round-3 rewrite in prose that wasn't touched by the renumbering edit (a Risks-table row, two mentions of "Step 0" that should say "step 3", and one "steps 2-3" that should name step 2 and step 4 separately).
- **B2 residue**: the corrected audit procedure (Step 0.5) was right, but three other spots in the document (Codebase Facts, and two ADR lines) still repeated round 2's superseded "13 unguarded dereference sites... +2 more in gestures scroll paths" language instead of the real count. Re-grepped directly: **11 total call sites, 6 genuinely unguarded** (`picker.ts:32,49,51,70`; `base.ts:84` — itself wrapped in a try/catch, so `assertEle()`'s throw there is caught and behaviorally inert; `utils.ts:1318` — the one site with no surrounding try/catch, so this is the single place `assertEle()` produces a real, user-visible behavior delta), **5 already guarded** (`utils.ts:908,958`; `gestures.ts:422,477,828` — matching Step 0.5's confirmed examples exactly). The phantom "+2 more in gestures scroll paths" does not exist.

Round 4 (this revision) fixes N1, N2, and the B5/B2 residue directly; the inventory, Decisions A/B/C, B3's corrected shapes, and the ADR's substance are unchanged and were reconfirmed correct across rounds 2 and 3 — they are not re-litigated here. Diffs from round 3 are called out inline as **[R3→R4]**.

## RALPLAN-DR Summary (short mode)

### Principles (3-5)
1. **No behavior changes on the success path.** [R1→R2: amended] Failure-path behavior may become an explicit thrown error where the current code already throws a `TypeError` one line later at an unguarded dereference (the 11 `| false` sites [R3→R4: corrected from 13]) — this is not a new failure mode, it's an earlier, named one. No other runtime logic changes.
2. **Reuse before invent, with an acknowledged limit.** Every `element`/`selector`/`context` param maps to an existing shape in `types.ts` or `enums/context-ref.ts` before any new type is authored — but `WdioElement`/`Selector` are index-signature `any`-equivalent one property access deep, so "reuse" closes the *duplication* gap, not the *safety* gap, except at the one boundary (§`| false`) where an honest union type is introduced.
3. **Respect the documented ambient-`any` decision** for `driver`/`browser`/`$`/`$$` (`globals.d.ts`) unless the user explicitly opts to revisit it.
4. **File-by-file, gated, monotone progression**: type → write vitest tests → compiler-enforced ratchet clean → package build clean → move to next file. [R1→R2: strengthened] Files are ordered so no later step can invalidate an earlier commit — producers before consumers, not smallest-first.
5. **Establish the WDIO-global mocking convention once, in the most representative early file**, then reuse it verbatim across the rest. [R1→R2: "smallest" replaced with "most representative" — see Decision C/S3]

### Decision Drivers (top 3)
1. User's explicit instruction: file-by-file with a verification gate per file, not one giant sweep — but the gate must be a compiler check, not a manual audit, since manual audit demonstrably missed 48 of 78 sites on this same file set.
2. The `| false` cascade forces a decision about Principle 1 before any consumer file (`picker.ts`, `base.ts`, `gestures.ts`) is typed — deciding it at step 8 (as round 1 did) invalidates 3 already-committed files.
3. Zero existing test precedent for `driver`/`$`/`$$` mocking — decide once, apply consistently.

### Viable Options

**Decision A — Compiler enforcement for the converted surface**
- **Option A1 (recommended, revised from round 1): scoped `noImplicitAny` ratchet.** Add `packages/core/tsconfig.strict.json` (`extends: "./tsconfig.json"`, `compilerOptions: { noImplicitAny: true }`, `files: []`) with an explicit, growing file list — each step appends exactly the file it converts. This is the per-file gate, replacing manual audit.
  - Pros: machine-checked, so Criterion #1 becomes falsifiable; blast radius is the explicit allowlist, not the whole package — *smaller* than round 1's "leave the flag off" option, since that option's containment was aspirational (nothing stopped a future edit from reintroducing implicit-any) while this one is enforced by `files: []`.
  - Cons: requires a small Step 0 (below) to unblock 2 files that would otherwise be permanently unverifiable under this gate (`aria-query`'s missing types, `ContextRef`/`DocumentReadyState`'s enum-indexing `TS7053`).
- **Option A2 (round 1's recommendation, now superseded): leave `strict:false`, rely on manual review.** Rejected — manual audit is the round-1 verification method, and it undercounted the actual surface by 2.6x on this exact file set. Kept here only as the documented alternative this plan explicitly did not choose.
- *Recommendation:* A1, via the scoped ratchet. Full `strict:true` (which pulls in `strictNullChecks`, flooding unrelated `null`/`catch` sites) and flipping the repo-wide `tsconfig.base.json` remain explicitly out of scope.

**Decision B — `driver`/`$`/`$$` typing depth**
- **Option B1 (recommended): keep ambient globals as documented `any`.** Type only the helper function signatures, not the global `driver`/`$`/`$$` shapes. Matches the existing documented rationale and the same convention in `packages/providers` and `packages/reporters`; verified mechanism: `services/utils.ts#addCommands` iterates namespaces generically, so narrowed helper signatures don't break registration.
- **Option B2 (revised from round 1 to remove a strawman): WDIO `Browser` interface module augmentation.** `declare global { namespace WebdriverIO { interface Browser { pressNativeAlertButton(selector: string): Promise<void>; ... } } }`, one method per registered custom command, replacing the ambient `any`.
  - Pros: closes the largest remaining `any` surface in the helpers layer; is the idiomatic WDIO-recommended pattern (`globals.d.ts`'s own comment names it), not a hand-rolled parallel type.
  - Cons: every `addCommand` call site needs the augmentation kept in sync going forward; touches 3 packages' `.d.ts` files; reverses a documented decision without being asked — out of scope for "convert these 8 files."
- *Recommendation:* B1, unchanged. B2 is a legitimate (not strawman) alternative, explicitly deferred as a named follow-up, not invalidated on the merits.

**Decision C — WDIO-global test mocking convention**
- **Option C1 (recommended): shared test-setup helper.** `packages/core/src/helpers/native/__test-helpers__/wdio-mocks.ts` exporting a `mockWdioGlobals()` using `vi.stubGlobal('driver', ...)` / `vi.stubGlobal('$', ...)` / `vi.stubGlobal('$$', ...)`. [R1→R2: built against `base.ts`, not `alert.ts` — see Implementation Steps] and imported by all 8 test files.
- **Option C2: inline `vi.stubGlobal` per test file, no shared helper.** Rejected — near-certain drift across 8 files with no existing precedent to anchor consistency.
- **Option C3 (new in R2): `@wdio/webdriver-mock-service`.** Already a dependency of `@caps/core`. Encodes WDIO's actual wire protocol rather than the team's belief about the element API surface.
  - Pros: higher fidelity than a hand-rolled mock for the element-protocol layer (`isDisplayed`, `click`, etc.); independent of the same author's mental model that also wrote the annotations (mitigates the compiler/test shared-blind-spot tension named below).
  - Cons: heavier setup; doesn't cover the custom-command layer (`driver.<customHelper>()`), so C1 is still needed there regardless.
- *Recommendation:* C1 for the ambient-global layer (`driver`/`$`/`$$` stubs), evaluated alongside C3 for the element-protocol layer during **step 3's** (`base.ts`) helper design [R3→R4: corrected from "Step 0" — the mock helper is authored in step 3, not Step 0] — if C3's setup cost is low once tried, prefer it for `isDisplayed`/`click`/etc. call chains since it's an independent check against the same `WdioElement` mental model the annotations use; if not, C1-only with the mitigation named in Risks below.

### Named tension: compiler and tests can share a blind spot

Because `WdioElement`/`Selector` are index-signature `any`-equivalent, annotating a param `el: WdioElement` still typechecks `el.thisMethodDoesNotExist()`. If the same person's mental model of the WDIO element API is wrong when writing both the annotation and the C1 hand-rolled mock, the mock and the annotation are wrong in the same direction and the test passes anyway — the compiler and the test suite are not independent checks at that boundary. This is why Decision C considers C3 (a mock built from WDIO's actual protocol, not the author's belief about it) as a partial mitigation, and why the `| false` policy below is typed as an honest union rather than folded into `WdioElement` itself — the one place in this file set where a real, currently-latent bug exists (`picker.ts:30-32` throws an unguarded `TypeError` today whenever a picker row isn't found) is exactly the place this plan makes the type honest rather than papering over it with a reused-but-permissive shape.

## ADR

- **Decision**: Convert the 8 native helper files to true TypeScript, ordered by dependency (producers before consumers: `find-strategy` → `utils` → `base` → `gestures` → `picker` → `carousel` → `web-view` → `alert`), gated by a scoped `noImplicitAny` ratchet (`tsconfig.strict.json`, rooted at the permanent `src/globals.d.ts` entry plus a growing `files` allowlist) plus build+test at each step; **the ratchet's pass condition is zero diagnostics scoped to `src/helpers/native/` or `src/globals.d.ts`, not raw `tsc` exit code** — `files` bounds root files only, so `utils.ts`'s transitive imports of 12 not-yet-fixed enum files contribute an accepted, logged, out-of-scope diagnostic baseline from step 2 onward rather than being silently absorbed or blocking the pass; reuse existing `types.ts`/`enums/context-ref.ts` shapes where they're genuinely reusable; type the `findEle`-family's `| false` return honestly and introduce `assertEle()` at the 6 genuinely-unguarded of 11 total dereference sites (5 are already safe via truthy narrowing and are left untouched); leave the ambient `driver`/`$`/`$$` globals as documented `any`; leave repo-wide `strict:false`/`tsconfig.base.json` unchanged.
- **Drivers**: user's explicit file-by-file/no-giant-sweep instruction, now enforced by a compiler ratchet instead of manual audit after manual audit demonstrably undercounted the surface 2.6x; the `| false` cascade forcing an explicit, upfront decision rather than a step-8 surprise; the ratchet's own scope needing to be decided explicitly (does `files` alone bound the checked program? — no) rather than assumed; avoidance of any-laundering on WDIO/Appium globals; respecting the pre-existing documented ambient-any design.
- **Alternatives considered**: manual-audit-only verification (Option A2, rejected — empirically unreliable on this exact file set); package-wide `strict:true` (rejected — pulls in `strictNullChecks`, unbounded blast radius); extending Step 0's enum fix to all 14 enum files so plain `tsc` exit-0 holds literally (rejected for this pass — would silently absorb most of Follow-up #1 into scope; the scoped-diagnostic gate achieves the same falsifiability without the scope creep); narrowing ambient `driver`/`$`/`$$` via WDIO `Browser` module augmentation (Option B2, legitimate alternative, deferred as a named follow-up rather than dismissed as a strawman); per-file ad-hoc test mocking (Option C2, rejected — drift risk); swallowing the `| false` cascade into `WdioElement`, or applying `assertEle()` uniformly to all 11 originally-flagged sites regardless of existing guards (rejected — the former launders the one real bug in scope, the latter would have converted a normal scroll-to-find retry-loop miss into an uncaught throw in a file with zero try/catch).
- **Why chosen**: resolves all reviewers' confirmed findings across three review rounds (2.6x undercount, wrong `ContextRef`/`findStrategy` types, mischaracterized `gestures.ts` anys, inverted file order, undecided `| false` policy, a ratchet config that didn't actually bound scope, and a blanket `assertEle()` application that would have broken working retry logic) while preserving the plan's original incremental, gated character and the user's stated risk tolerance.
- **Consequences**: `packages/core` outside `helpers/native` still permits implicit-any until a follow-up extends the ratchet package-wide; the scoped-diagnostic gate means an out-of-scope enum-`TS7053` count is a permanent, visible fixture of the per-file verification output from step 2 onward until Follow-up #1 lands — this is a deliberate, logged tradeoff, not noise to suppress; `assertEle()`'s throw is a real (if narrowly scoped, and inert at one of its two live call sites due to an existing try/catch) behavior change that must be called out in the PR description, not just this ADR; the WDIO mock helper (and possibly `@wdio/webdriver-mock-service`) becomes shared test infrastructure other native-helper work should adopt going forward.
- **Follow-ups**: (1) evaluate extending `tsconfig.strict.json`'s `files`/enum-fix scope to the rest of `packages/core` (the ~195 out-of-scope diagnostics — mostly mechanical: ~70-84 are the same enum-`props` pattern across the 12 remaining enum files, ~23 are 2 more untyped-module shims, the rest genuine, concentrated in `helpers/browser/utils.ts` and `services/*`); once this lands, the scoped-diagnostic gate can revert to plain exit-0; (2) if the team wants a precise `WebdriverIO.Browser`-based ambient type (Option B2), scope it as its own change spanning `globals.d.ts`, `providers/wdio-globals.d.ts`, and `reporters/global.d.ts` together; (3) if C3 (`@wdio/webdriver-mock-service`) proves valuable during step 3, consider migrating the ambient-global stubs (`driver`/`$`/`$$`) to it as well, not just the element-protocol layer.
